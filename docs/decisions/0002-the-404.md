# 0002. The 404 is a real prerendered page, reached by a proxy rewrite

Status: accepted. Supersedes an earlier draft of this record that only covered `loading.tsx`.

## Context

The site needs a localized 404 that keeps the header, footer and language. The obvious App Router
answer is `not-found.tsx` plus a catch-all route that calls `notFound()`.

That was built first, and it does not work with this route shape.

## What was measured

The root layout must live at `app/[locale]/layout.tsx`, because root parameters are only the dynamic
segments **above** the root layout and `next/root-params` is how the locale reaches the content. So
there is no `app/layout.tsx`, and therefore nowhere to put a root-level `not-found.tsx`.

With `app/[locale]/[...rest]/page.tsx` calling `notFound()` and `app/[locale]/not-found.tsx`
providing the UI, on Next 16.3.5:

| Observation | Result |
| --- | --- |
| HTTP status | 404, correct |
| Document | `<html id="__next_error__">`, Next's bare error shell |
| Rendered body | **190 characters, effectively empty** |
| Stylesheet | absent |
| Header and footer | absent |
| The 404 copy | present only in the RSC flight payload |

So the copy arrived after hydration. A visitor saw a blank flash, and a visitor without JavaScript
saw nothing at all. Note that a status-only check passes this: the defect is invisible unless you
assert on the server-rendered body, which is why the URL matrix now strips the flight payload before
looking for the copy.

`experimental.globalNotFound` was then tried, and it does not help either. That file only handles
requests matching **no** route, and the proxy rewrites every request into the locale segment, so
nothing ever fails to match. A minimal `global-not-found.tsx` was never reached, with the flag
confirmed active in the build output.

## Decision

`app/[locale]/404/page.tsx` is an ordinary, statically generated page, and `src/proxy.ts` rewrites
unknown paths to it with a 404 status:

```ts
if (!KNOWN.has(pathname) && !REDIRECTABLE.has(pathname)) {
  const url = request.nextUrl.clone()
  url.pathname = `/${locale}/404`
  return NextResponse.rewrite(url, { status: 404 })
}
```

A rewrite rather than a redirect, so the URL the visitor typed stays in the address bar.

Verified result, on every unknown path in both locales: status 404, correct `lang`, full header and
footer, stylesheet linked, and the copy present in the server-rendered HTML with no JavaScript
required.

The page carries `robots: { index: false, follow: true }`, and it is deliberately absent from
`PAGES`, so it never enters the sitemap.

## Two traps this leaves behind

**The `REDIRECTABLE` set is not optional.** The known-path check runs before next-intl, so the first
version of it returned 404 for every `/tr/...` path, killing the redirect that collapses the
superfluous default-locale prefix onto the canonical URL. That is duplicate content in one
direction and a broken link in the other. The URL matrix caught it, and section 3 exists to keep
catching it.

**Dotted paths are excluded on purpose.** The proxy matcher's `.*\..*` clause means `/veltrex.pdf`
never reaches the proxy and gets Next's own unbranded 404. Narrowing the matcher would mean
enumerating every real asset extension, and a request for a non-existent file is not a page view
worth branding.

## No loading.tsx, anywhere

Unchanged from the earlier record, and it interacts with the above.

`not-found.js` is wrapped by `loading.js`'s Suspense boundary, and not-found returns **200 for
streamed responses**, 404 only for non-streamed ones. So a single `loading.tsx` would turn every 404
into a soft 404: the page still reads "not found" to a human and still returns 200 to a crawler.

The cost of shipping none is zero, because every page is prerendered at build time. There is no data
fetch to wait on, so there is no loading state to show.

The current architecture no longer depends on the not-found boundary, so this is now belt and
braces rather than the primary defence. It stays because a future contributor adding a `loading.tsx`
would otherwise reintroduce the soft-404 risk the moment anyone reinstates a not-found boundary.

The verification chain asserts the **status code** of six different 404 shapes before it looks at any
body, precisely because the body is not where these defects show up.
